A Docker environment for running Chromium with **Chrome DevTools Protocol (CDP)** support.

The image is meant to be **driven externally over CDP** — for example by
BrowserHive, a web page capture server. What the image decides, and what it
leaves to the client:

- **The CDP client decides** how to use tabs and browser contexts; the image
  enforces nothing — see [Driving model &amp; dbus](/internals/driving-model/).
- The **Back-Forward Cache (bfcache) is off**, so going back through history
  still issues requests that CDP's `Fetch` and `Network` domains can see — see
  [Chromium flags](/configuration/chromium-flags/).
- The container has **no desktop environment**, so the credential store is
  pinned to `basic` and D-Bus is limited to a per-process session bus. System-bus
  probes still fail and leave known noise on stderr.

## The image

| Target | Purpose |
| ------ | ------- |
| **Production** | Headless Chromium, minimal footprint (no Node.js / dev tools). CDP on port `9222` via `socat`. → [Production](/getting-started/production/) |

The former headful images (the containerized development environment and the
`debug` VNC target) are mothballed under `attic/` — visual verification now
uses the `chrome://inspect` screencast against headless workers. See
[Verifying workers](/getting-started/verify/).

## How it fits together

```
   CDP client (e.g. BrowserHive)
            │  connects to :9222
            ▼
   ┌─────────────────────────────┐
   │ chromium-server container   │
   │   socat  :9222 → 127.0.0.1:9223
   │   chromium (CDP)            │
   └─────────────────────────────┘
```

A CDP client connects from outside and drives Chromium over CDP; the container
itself has no UI. To watch a tab render, open the worker in the
`chrome://inspect` screencast — it works against headless workers
(see [Verifying workers](/getting-started/verify/)).
